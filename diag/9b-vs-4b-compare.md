## 二、方案 A 改了什么（代码级）

### 1. manager 侧：自适应降档阶梯（根治）

`webui/manager.py` → `resolve_launch()`：

```
档位阶梯（用户原设定永远第一档，能全层上卡就一个字都不改）：
  ① 原设定                        （f16 KV + 用户 batch）
  ② f16 KV + b512/ub128          只缩 batch —— 对质量零损伤，计算缓冲 501→150 MiB
  ③ q8_0 KV + b512/ub128         KV 近无损
  ④ q4_0 KV + b512/ub128         有损，但换回全层上卡
阶段二（①②③④ 都还掉层时，例如 np=4 把 KV 池撑大）：
  ⑤ 问一次「ctx 降到多少能全层上卡」，够用就降（下限 8192），换回全层
```

- 返回 `applied_ctk / applied_ctv / applied_batch / applied_ubatch`，
  `start_instance()` **用这几个值组命令行**（关键，否则降档白算）。
- 熔断开关：环境变量 `LLAMA_NO_AUTO_LADDER=1`，或请求体 `"auto_ladder": false`。
- 顺带：`fit_plan()` 加了成功结果缓存 —— 阶梯最多要跑 5 次预演，不缓存每次加载多等十几秒。

### 1.1 测试中新发现：预演结论会「随时间漂移」（已加 TTL 兜住）

调试时撞到一件很反直觉的事：**同样的模型 + 同样的参数，`llama-fit-params` 的层数结论会变**。
例如 4B @128K / q8_0，几分钟内先报 `-ngl -1`（全层），再报 `-ngl 30`（掉两层）。
根因没有完全定位（怀疑与当时的机器状态 / 驱动侧可用显存有关），但后果很明确：

> 如果把「全层可行」这个乐观结论**永久缓存**，看起来是省时间，
> 实际上会把某一次比较乐观的采样冻结成永久答案 —— 下次显存紧张时就不再降档，直接掉层。

所以缓存改成 **带过期时间**：`FIT_PLAN_TTL = 120.0` 秒，缓存键是 `tuple(args)`，
存 `(时间戳, 结论)`，过期即为未命中。真正兜底的是启动参数里的 `-fit on -fitt 512`——
它在**真正启动那一刻**按当时空闲显存再拟一次，这是唯一可信的最终裁决。

### 2. 前端侧

- 性能页「Preflight」多了 **auto-tuned** 提示：显示真正会下发的 `KV / batch / ctx`，
  不再让界面参数与实际加载参数"两张皮"。
- 修了一个原有隐患：预演曾**写死 `batch: 512/ubatch: 128`**，预设若是 2048/512，
  预演会比真实启动乐观 350 MiB。现在跟随预设。
- `measureKv()`（只测 KV 字节/token）显式传 `auto_ladder: false` —— 否则测到的是降档后档位（q4_0）的值，存进 f16 的键就全错了。

## 三、实测数据（同机同晚，96–200 token 生成）

### 3.1 9B `qwen3.5-9b-defiant`（Q4_K_M，6.36 GiB）六种配置

| 配置 | 上卡层数 | 生成 tok/s | 预处理 tok/s |
|---|---|---:|---:|
| np=1 **f16 KV + b2048/512（你的原配置）** | 25/32 | 24.0 | 51 |
| np=1 f16 KV + b512/128（只缩 batch） | 28/32 | 23.9 | 80 |
| np=1 q8_0 KV + b512/128 | 31/32 | — | — |
| **np=1 q4_0 KV + b512/128（方案 A 的落点）** | **全层 32/32** | **33.0** | **200** |
| np=4 f16 KV + b2048/512（多槽预设） | 24/32 | 20.6 | 51 |
| np=4 q4_0 KV + b512/128 | 31/32 | 25.2 | 77 |
| np=1 q8_0 KV + **128K 上下文** | 19/32 | 13.7 | 19 |

> 「上卡层数」是 `llama-fit-params` 的预演值；`-fit on` 启动时还会按当时的真实空闲显存再拟一次，
> 所以实测速度与层数**不完全单调**（如 25/32 与 28/32 打平）。

**为什么掉层没那么致命**：qwen3.5 是混合线性注意力（`full_attention_interval=4`，
32 层里只有 8 层有真 KV），CPU 侧那些层每 token 只需搬运很小的递归状态，
不是"搬整个 KV 块"。所以 25/32 层仍有 24 tok/s；**真正的地板是"几乎没有层在 GPU 上"**（见第四节）。

### 3.2 新模型 `Qwen3.5-4B-Uncensored-HauhauCS-Aggressive · Q6_K`

| 配置 | 上卡层数 | 生成 tok/s | 预处理 tok/s |
|---|---|---:|---:|
| **f16 KV · 32K · np=1（推荐）** | 全层 | **48.7 / 52.3** | 244 / 256 |
| f16 KV · 32K · **np=4** | 全层 | **57.6** | 306 |
| f16 KV · **128K** | 25/32 | 28.4 | 53 |
| q4_0 KV · 128K（自适应会给的档） | 全层 | — | 设备 4793 MiB，能全层 |

### 3.3 交替配对测（抵消笔记本功耗漂移）

| 轮次 | 9B（自动降档后） | 4B Q6_K |
|---|---|---|
| 第 1 轮 | 30.3 tok/s / 预处理 182 | 57.4 tok/s / 预处理 254 |
| 第 2 轮 | 18.7 tok/s / 预处理 127 | 51.5 tok/s / 预处理 250 |

**4B 是 9B 的 1.9×（生成）/ 1.4×（预处理）**，而且 **4B 稳定得多**（51–58 波动 vs 19–33）。
原因很实在：4B 只占约 4.5 GB，留出 ~2 GB 显存余量；9B 要占 6.4 GB，贴着卡顶跑，
Windows/WDDM 一旦回收页面，token 速度就抖。

## 四、关于你说的「2 tok/s」——我没能复现，以及最可能的原因

同一份 9B、你原来的配置（f16 KV + b2048/512），我这里实测 **20.7–24.0 tok/s**，不是 2。

你当时说过一句关键的话：**「显存基本上是满的」**。这大概率就是答案：

> 只要有**绝大部分权重留在 CPU**，就是纯 CPU 推理 6.36 GiB 的 Q4 模型 → **2–4 tok/s**，与你的体感吻合。
> 而"几乎没有层能上卡"只会发生在**加载那一刻显存已被别人占满**的情况。

能把你 8 GB 吃到没余量的常见来源：
1. **动态壁纸（Lively）+ 播放器（mpv）+ 多个 Edge/WebView2** —— 我这边基线就有 ~1.3–1.5 GB；
2. **残留的 llama-server 进程**（外壳/`.bat` 手工起的实例不在 manager 的表里，换模型时未必被杀掉）；
3. 多槽（`np=4`）+ 长上下文（128K）叠在一起 —— 实测这一档只有 19/32 层、13.7 tok/s，再挤一点就是地板。

**下次觉得慢，一条命令就能定位真相**（会同时打印：实际加载的模型、上卡层数、tok/s）：

```bash
node D:/llama/tools/model/bench_speed.mjs
curl -s http://127.0.0.1:8090/api/gpu-cleanup        # 看显存被谁占着（只读）
```

判读：**上卡层数 < 20 层 = 当时显存被占了**，去性能页点「清理」或关掉吃显存的程序即可。

## 五、选型：为什么是 4B Q6_K

你的搜索条件（`≤6B` + `uncensored` + 按下载量）真实榜单里，前 10 名有 6 个是 **27B/35B**——
它们下载量高是因为下载者手里是 24 GB/48 GB 卡（`Qwen3.8-27B` 系 Q4_K_M 约 16.4 GB）。
**筛选口径必须是「设备账本 ÷ 你的预算」，不是下载量排序。**

| 候选（来自你的榜单） | 文件 | 设备合计 | 今天全层上卡？ | 实测/预计 |
|---|---:|---:|---|---:|
| **Qwen3.5-4B-Uncensored-HauhauCS-Aggressive · Q6_K** 🥇 | 3.23 GiB | ~4500 MiB | ✅ 余 1.9 GB | **48.7–57.6 tok/s（实测）** |
| 同一个 · Q8_0（要更高质量时） | 4.17 GiB | ~4200 MiB | ✅ | 约 40–48 tok/s |
| 同一个 · Q4_K_M（最省） | 2.52 GiB | ~3000 MiB | ✅ 余 3.4 GB | 约 65–75 tok/s |
| Qwen3.5-2B-Uncensored · Q6_K | 1.45 GiB | ~1900 MiB | ✅ | 约 100+ tok/s（质量略降） |
| Gemma-4-E2B-Uncensored · Q4_K_P + mmproj | 3.21+0.94 GiB | ~4400 MiB | ✅ | 带视觉+音频，但 E2B 有效参数小 |

**选它的四个理由**：① 与你的 9B 同属 `qwen35` 架构（SSM 混合、KV 极小，32K 只吃 ~340 MiB）；
② Q6_K 相对 BF16 几乎无损；③ 3.23 GiB 只占卡的一半，**不用管桌面在干什么也不会掉层**；
④ 仓库里带 `mmproj-…-BF16.gguf`（0.63 GiB，arch=`clip`，已下载）→ **它还是视觉模型**。

## 六、遗留事项

1. **mmproj 目前不会自动挂上**：`manager.py` 只做「扫盘时过滤投影层」，不会给 llama-server 加 `--mmproj`。
   要用视觉，得手工起一次：
   `bin\llama-server.exe -m models\hf\…-Q6_K.gguf --mmproj models\hf\mmproj-…-BF16.gguf -c 32768 -fa on`
   （想要的话我可以给 manager 加「自动配对同名 mmproj」——约 20 行。）
2. **`-fit` 的层数是预演值**，启动时还会按真实空闲显存再拟一次，所以"预演 25/32"实测未必就是 25；
   而且这个预演结论**本身会随时间漂移**（见 1.1），只能当参考，不能当承诺。
3. **128K 上下文会掉层**：9B 与 4B 都一样（4B 128K+f16 只剩 25/32）。
   长上下文请让自适应降档接管（它会给 q4_0 KV，4B 在 128K 下能全层）。
4. **测量噪声**：笔记本 GPU 功耗/温度漂移会让同一配置差出 1.6×，所以本文都给了区间与配对结果。
