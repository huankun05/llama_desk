# 9B 只有 2 tok/s 的原因与提速方案

> 2026-09-21 实测。数据来自 manager 的 fit 预演（`/api/instances`）、`/api/gpu-cleanup` 与 `nvidia-smi`。

## 一、实测账目

| 项 | 值 |
|---|---|
| 显卡 | RTX 4070 Laptop，**8188 MiB** |
| 整卡已用 | 7602 MiB |
| **llama-server 占用** | **6463 MiB** |
| 其他程序占用 | 1139 MiB |
| **上卡层数** | **28 / 32**（4 层落在 CPU） |
| 启动参数 | `-c 32768 -ctk f16 -ctv f16 -np 1 -kvu -fa on -t 8 -b 512 -ub 128 -fit on -fitt 512` |

manager 的预演结论原文：

> 预演：28 层上卡（约 88%），其余走 CPU，生成速度会明显下降

## 二、为什么只有 2 tok/s

**只要有层落在 CPU，每生成一个 token 就要把这几层的中间结果在 CPU 与 GPU 之间来回搬运 32 趟**，
PCIe 带宽和同步延迟直接主导了耗时 —— 所以 2 tok/s 是「4 层在 CPU」的必然代价，不是模型本身慢。

**为什么只上 28 层**（fit 的预算算不过）：

```
9B 的 Q4_K_M 权重          6513 MiB   ← 卡容量的 80%
KV cache（f16 @ 32K）       ≈ 600 MiB
计算缓冲（b=512/ub=128）     ≈ 350 MiB
──────────────────────────────────────
全 32 层需要                ≈ 7277 MiB

实际可用（fit 预算）         = 6537 MiB  （8188 − 系统 1139 − 保留 512）
                            ──────────
                            差 740 MiB
```

**根因：这个 GGUF 文件本身太大。** 6513 MiB 摆在 8188 MiB 的卡上，
留给 KV cache 和计算缓冲的余量不足一个 GB。

## 三、加速方案

| 方案 | 具体做法 | 预期速度 | 代价 |
|---|---|---|---|
| **① 转低量化（推荐）** | `bin\llama-quantize.exe` 把 9B 转成 **Q3_K_M**（≈4.5 GiB） | **15–25 tok/s（约 10×）** | 质量略降；转换要几分钟 + 约 4.5 GB 磁盘 |
| **② 调参数 + 腾显存** | ① KV 精度换 **q4_0**（KV 600→338 MiB）② 关掉其他吃显存的程序（系统占用 1139→约 600） | 有希望全层上卡 | 什么模型都不换，但余量紧，可能仍差一点 |
| **③ 换小模型** | qwen3-4b（2.3 GiB）/ MiniCPM5-2B（1.6 GiB） | 30–50 tok/s | 能力下降 |
| ④ 只加 CPU 线程 | `-t 8` → `-t 16` | 2 → 3–4 tok/s | 治标：那 4 层算得快一点而已 |

### 在哪里改

- **KV 精度 / 上下文**：`#/parameters` 页的 **KV precision (-ctk/-ctv)** 与 **Context (-c)**；
  或 `#/performance` 页针对单个模型的「模型专属参数」卡（推荐按模型存，别改全局默认）。
- **空闲卸载**：`webui.idleTtl`（默认 300 秒）。设成 `0` = 常驻不卸载。
  ⚠️ 空闲卸载会连**正在提供 WebUI 的那个服务**一起卸掉，习惯切出去再回来的话建议设 0。

### 两个反直觉的点

1. **8B 反而比 9B 更吃显存**。同样是 32K/f16，fit 预演是 8B **25/36 层**、9B **28/32 层**。
   因为 Qwen3 是标准注意力（每层都存完整 KV），而 **qwen3.5-9b 是混合线性注意力（arch `qwen35`）**，
   绝大多数层只存递归状态，KV 极小（32K+q4_0 实测才 338 MiB）。
   → **"换个参数少一点的模型"不一定更划算，要按 KV 架构分别算。**
2. **别硬编码 `-ngl`**。只要显式给了 `-ngl` / `-ot` / `--tensor-split` / `-ncmoe` 中任意一个，
   llama.cpp 的 fit 就会 abort、退化成全塞 device 0 → `cudaMalloc` OOM。正确写法是 `-fit on -fitt 512`。

## 四、横向对照（都按 32K / f16 KV）

| 模型 | 权重 | 上卡层数 | 说明 |
|---|---|---|---|
| qwen3.5-9b-defiant | 6513 MiB | **28 / 32** | 混合线性注意力，KV 极小；瓶颈纯在权重 |
| qwen3-8b | 4795 MiB | **25 / 36** | 标准注意力，KV 大，比 9B 更吃亏 |
| qwen3-4b | 2382 MiB | 33 / 36 | 接近全上卡 |
| MiniCPM5-2.6B | ≈1.6 GiB | **全层** | 最稳 |

## 五、推荐动作顺序

1. **先做免费的**：把 9B 的 KV 精度改成 `q4_0`，关掉浏览器等占显存的程序，重新加载。
   看性能页 fit 结论有没有变成「全层可上卡」。
2. **还是掉层** → 转 Q3_K_M（方案 ①）。
3. **想立刻流畅** → 先用 MiniCPM5 / qwen3-4b 顶着，9B 留给需要质量的场合。
