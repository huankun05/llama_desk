# 生成为什么慢：实测归因报告

日期：2026-09-22 · 机型：COLORFUL X15 AT 23（i7-13700HX + RTX 4070 Laptop 8 GB / 8188 MiB）
驱动 616.56 · 插电 · 电量 100% · 电源计划「高性能」
全部数字来自本机实测。

## 一、结论

**这个配置在这台卡上的稳态速度就是 44.6 ~ 46.4 tok/s。** 四次测量（共 4100 token 连续生成）：

| 指标 | 稳态实测值 |
|---|---|
| 生成速度 | **46.37 / 45.62 / 44.57 / 45.20 tok/s** |
| GPU 实际功耗 | **75 ~ 105 W** |
| GPU 强制功耗上限（enforced） | **133.75 ~ 140 W —— 全程没触顶，只用到一半多** |
| GPU 温度 / SM 频率 | 78 ~ 88 °C / 2235 → 2070 MHz |
| **CPU 温度区（tz0）** | **88 ~ 99 °C**（连 GPU 空载时都是 88~98 °C） |
| 降频标志 | `SW Thermal Slowdown` / `SW Power Cap` / `HW Thermal Slowdown` **全部 Not Active** |
| 显存 | 6723 MiB 已用 / 1226 MiB 空闲（128K + q4_0 KV） |

**照这个数：45 tok/s × 3.3 GB 权重 ≈ 150 GB/s 有效权重读取带宽**，已接近这块卡（256 GB/s 峰值）
的实用上限。（*推论，非实测定论*：生成很可能是**访存受限**；若成立，则「GPU 只吃 80 W」是
**结果**而非原因 —— 访存型 kernel 烧不动 SM。）

**一句话**：慢不是「被什么压住了」，而是**它在正常状态下的速度就这么快**。

## 二、第二轮对照实验（决定性）

同一台机器、同一模型、同一参数（ctx 131072 + `-ctk/-ctv q4_0` + `-np 1`），
在 **CPU 温度区全程 97~99 °C** 的条件下：

```
400 token  → 46.37 tok/s   GPU 83 W / 80 °C
400 token  → 45.62 tok/s   GPU 82~85 W / 85 °C
1800 token → 44.57 tok/s   GPU 75~86 W / 84→88 °C   SM 2235→2070 MHz
1500 token → 45.20 tok/s   enforced 上限 133.75~140 W 全程，GPU 只画 75~83 W
```

生成结束后立刻读降频原因：

```
SW Power Cap        : Not Active      HW Thermal Slowdown : Not Active
HW Slowdown         : Not Active      SW Thermal Slowdown : Not Active
Board Limit         : Not Active      HW Power Brake      : Not Active
```

### 2.1 CPU 温度时序（与上表同一次实验）

| 阶段 | CPU tz0 | GPU 功耗 | 说明 |
|---|---|---|---|
| **GPU 完全空载**（6.4 W / 210 MHz） | **88 ~ 98 °C** | 6 ~ 7 W | ← 关键：CPU 温度区**空载就这么高** |
| 模型装入显存 | 89 ~ 98 °C | 24 ~ 27 W | 0~10% util，纯拷贝 |
| 生成中 | **97 ~ 99 °C** | 80 ~ 105 W | 照样满血 |
| 生成后静置 | 89 ~ 98 °C | 7 W | 又回到「空载 90 多度」 |

**⇒ CPU 温度区在这台机器上基本常驻 90~99 °C，不随负载变化 ⇒ 它根本不是个「变量」。**
用它做归因，等于用一个常量去解释一个变量。

## 三、被证伪的假说

| 假说 | 判决 | 证据 |
|---|---|---|
| **「CPU 过热 → GPU 功耗被压制」** | ❌ **证伪** | CPU tz0 **97~99 °C 的同时**，GPU 稳定吃 **80~105 W**、跑 **44.6~46.4 tok/s**，且全部降频标志 Not Active。CPU 热到这个程度，完全不妨碍 GPU 满血 |
| 「GPU 被功耗上限压住」 | ❌ | 现在的 enforced 上限是 **140 W**，而 GPU 只画到 **80 W** —— **离上限还差 60 W**，根本不是撞墙 |
| 「`SW Thermal Slowdown` 累积 ⇒ 在热降频」 | ⚠️ **这句话本身没错，但它推不出「CPU 害的」** | 初版就是这么从「计数器涨了」跳到「热源在 CPU 侧」的 —— **典型的从相关当因果**。第二轮实测：这个计数器**全程为 0 增长** |
| 「下的是 BF16，太大所以慢」 | ❌ | `model_ftype = Q6_K`。BF16 只是 GGUF 内部 `general.name` 的残留标签 |
| 「128K 上下文拖慢生成」 | ❌ 只占一小部分 | 285 → 65565 tokens 只衰减 **1.38×**（47.4 → 34.4） |
| 「层掉到 CPU 了」 | ❌ | 预处理 **1657 tok/s**（4663 token / 2.8 s）；掉层会同时拖垮预处理 |
| 「有别的 llama-server / 孤儿抢卡」 | ❌ | `/api/gpu-cleanup` 只有 1 个托管实例、`orphans: []` |
| 「电池 / 省电模式」 | ❌ | 插电、100%、电源计划「高性能」、CPU 最高性能状态 100% |

## 四、仍然没解释的部分（诚实记录）

**09:36–09:50 那段的 26.4 / 24.9 / 20.2 t/s（以及截图里的 14.76 t/s），本轮没能复现。**

同一台机器、同一模型、同一参数，现在稳定 44.6~46.4 —— **快了一倍**。造出这个差别的因素，
我手里只有候选，**没有一个被验证过**：

| 候选 | 支持 | 反对 |
|---|---|---|
| 当时的 **enforced 功耗上限是 115 W**（初版报告表格记录：`Current 115 / Default 115 / Max 140`），现在是 **140 W** | 这是两轮之间唯一**被同一条命令量到**的确凿差异 | 115 W 也不该把实际功耗压到 40 W（它只画到 80 W 就够跑 45 tok/s 了）⇒ **解释不了 40 W** |
| 当时有别的 **GPU 消费者抢显存带宽/时间片**：Lively 视频壁纸（`mpv.exe` 常驻）、6 × `msedgewebview2`、4 × Electron、微信小程序 —— 空载就占掉 **~1.9 GB 显存** | 能解释「利用率 90~100% 但功耗只有 40 W、SM 频率还没掉」这种**等待型**特征 | 这些都是常驻进程，本轮它们照样在跑，却没拖慢 |
| 当时我自己在同机跑重活（`cargo build --release` + `cargo build` + `npm run build`，随后又是长生成探针 + 1 Hz WMI 轮询） | 时间上吻合 | 不能解释「冷机短生成也只有 34 W」 |

**⇒ 结论：不下结论。** 下次再慢，按 §5 现场抓数。

## 五、下次慢了，按这个抓（现场判据）

```bash
node tools/diag/gpu_health.mjs          # 一张快照：功耗/上限/温度/降频原因/谁占显存
node tools/diag/ctx_speed_probe.mjs     # 生成速度 vs 上下文长度曲线
node tools/model/bench_speed.mjs        # 当前已载模型跑一次
```

**只在慢的那一刻、同一个时间窗里**同时记下这四个数：

| 记什么 | 判读 |
|---|---|
| `enforced power limit`（`nvidia-smi -q -d POWER`） | 掉到 100 W 以下 ⇒ EC 换了功率档，这才是「被压住」的硬证据 |
| `power.draw` | 与 `tg` 一起看：**先有速度还是先有功耗**（本轮证明二者同向，但方向未定） |
| 降频标志（`-q -d PERFORMANCE`） | 只有 `HW Thermal Slowdown: Active` **且**温度 ≥87 °C 才是 GPU 撞自己的热墙 |
| `tg` 基线 | **本机基线 = 44.6~46.4 tok/s @ 128K/q4_0**。显著低于它才算异常 |

口诀：
- **`draw` 远低于 enforced 上限 + 降频标志全 Not Active ⇒ 卡不是被压住的，是在等** → 查「谁在 GPU 上」。
- **CPU tz0 在 88~99 °C 之间都算正常**，别拿它当证据。
- **`model_alias` 会骗人**，真实量化只看 `/props` 的 `model_ftype`。

## 六、这次错在哪（写给自己）

1. **从「相关」直接跳到「因果」。** 看到 `SW Thermal Slowdown` 计数在涨 + CPU 在忙，
   就断定「CPU 的热抢了 GPU 的电」。**缺的是对照实验** —— 而对照实验的成本只有 3 分钟。
2. **把 CPU「负载」当成 CPU「热度」。** 7.48 核是**负载**证据，我从来没测过 CPU 温度就写了
   「热量主要来自 CPU 侧」。这次一测：**空载就 88~98 °C**，根本是个常量。
3. **`Current Power Limit` 只读了一次。** 它是个会变的量（EC 控制），单次读数不能当基线。
4. **正确的做法**：先跑一次**正常态基线**（速度 + 功耗 + 上限 + 降频标志），
   下次异常时再抓同一组数**对比**。没有基线，任何「异常」都不可证。
