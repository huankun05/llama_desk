| 通路 | 谁发起 | 打到哪 | 用途 |

## 2. 为什么是这个形状（三个非显然的决策）

### 2.1 WebUI 由 llama-server 自己服务 ⇒ 端口不能换

页面 origin = `http://127.0.0.1:8080`，而 `localStorage`（对话历史、启动方案、界面偏好）绑在 origin 上。
换端口 = 换 origin = **全部本地数据丢失**。

所以「懒加载」不能靠「不起 llama-server」，只能靠**起一个不加载权重的空壳**：
llama-server 不给 `-m` 会自己进 **router 模式** —— 照常监听、照常供 WebUI、`/health` 立刻 200，
但 `model_path == "none"`、零权重、显存≈0。前端把这种状态叫 `isSentinel`，
`isRouterMode` 对它返回 `false`、`isModelMode` 返回 `true`，于是整套单模型 UI 把空壳当普通单模型服务用。

**代价**：几十 MB 内存。**收益**：用户的全部本地数据不丢。

### 2.2 中文靠运行时注入，不碰构建产物

`ui-src/overlay.js`（90 KB）在页面加载后按 **整文本节点的精确等值** 查 `DICT` 表替换。
好处：官方 UI 升级后不用重新翻译整个工程。代价：**不支持子串**，带插值的文本永远命中不了。

三条改 UI 的路径成本差很多：

| 改什么 | 改哪里 | 生效方式 | 耗时 |
|---|---|---|---|
| 中文词条 / 漏翻 | `ui-src/overlay.js` | `python tools\build\deploy_overlay.py` | 秒级 |
| 组件 / 交互 / 页面 | `ui-src\work\src\` | `ui-src\build-deploy.bat` | 1~3 分钟 |
| 窗口 / 启动 / 后端能力 | `app\src-tauri\src\` | `app\build.bat` | ~2 分钟（cargo） |

### 2.3 模型生命周期全在 manager 手里

```
懒加载：哨兵（无模型）──首次发消息──▶ ensureModelReady() ──▶ /api/switch ──▶ 真模型
空闲：  真模型 ──300s 无请求──▶ 看门狗卸载 ──下次发消息──▶ 同一条 ensureModelReady() 路径
```

`ensureModelReady()` 一次覆盖「哨兵」和「休眠」两种情形，**绝不抛异常**
（manager 没起 / 404 / 没睡着一律安静放行），所以不新增失败模式。

## 4. 性能

### 4.1 本轮实测发现的三个问题

#### ① 🔴 每 30 秒白读 1.2 GB 磁盘，并烧掉 1 个整核约 4 秒

`_do_scan()` 由 `_refresher` **每 30 秒**调用一次，而它内部对**每个** GGUF 调 `parse_gguf()`，
后者 `f.read(min(32MB, size))` —— **每个文件读 32 MB**。

实测（38 个 gguf）：

| | 数值 |
|---|---|
| 单次扫描读盘 | **1216 MB** |
| 单次扫描耗时 | **3851 ms** |
| 持续读盘速率 | **40.5 MB/s**（永远不停） |
| 开 8 小时累计白读 | **≈ 1.14 TB** |
| CPU 实测 | 每 30s 出现一次 **1.00 核**、持续约 4 秒的尖峰；均值 0.070 核 |

CPU 采样图（修复前），尖峰位置精确落在 30 秒周期上：

```
  t+ 26.1s    0.15  ##############################
  t+ 28.1s    0.94  ############################################################
  t+ 58.3s    0.10  ####################
  t+ 60.3s    1.00  ############################################################
```

**根因**：`parse_gguf()` 没有记忆化，而 GGUF 在程序运行期间**从不会被改写**。

**修法**：加一层 `(size, mtime_ns)` 键的缓存（`parse_gguf_cached()`），空结果不缓存
（解析失败下次要重试，缓存住等于把瞬时故障固化）。

实测效果：

| | 修复前 | 修复后（冷） | 修复后（热） |
|---|---:|---:|---:|
| 扫描读盘 | 1216.0 MB | 1216.0 MB | **0 MB** |
| 扫描耗时 | 3851 ms | 3851 ms | **0.1 ms** |
| CPU 峰值 | **1.000 核** | — | **0.016 核** |
| CPU 均值 | 0.070 核 | — | **0.007 核** |

正确性：`/api/models` 的返回 **JSON 逐字节一致**（16 条目整份比对），
逐字段比对 38/38 一致。

> 附带确认：`limit=32MB` 是安全上限，实测 KV 段最大偏移仅 **15.05 MB**，无截断。
> 另外试过「按需翻倍读取」把冷路径也压下来，**反而更慢**（11046 ms，因为每次翻倍都要从头重解析）——
> 已放弃，只保留缓存。

#### ② 🔴 `_sys_refresher` 定义了却从未启动 ⇒ CPU 信息永久为 null

`__main__` 里只起了 `_refresher` 和 `_idle_watchdog`，**漏了 `_sys_refresher`**。
而全代码里只有 `_collect_metrics()` 用 `get_cpu_static(block=False)`（只读缓存、不填缓存），
**没有任何地方调阻塞版** ⇒ `_sys_static["data"]` 永远是空的。

实测对比：

| | `cpu_name` | `cores` | `threads` | `max_mhz` |
|---|---|---|---|---|
| 修复前 | `null` | `null` | `null` | `null` |
| 修复后 | `13th Gen Intel(R) Core(TM) i7-13700HX` | `16` | `24` | `2100` |

⇒ 性能页「CPU」一栏以前**永远是空白**。启动线程即修好。

#### ③ 🟡 `GET /api/gpu-cleanup` 稳定 2.0 秒，且这笔钱由用户付

该接口只能靠 PowerShell + WDDM 性能计数器取「按进程显存」（本机
`nvidia-smi --query-compute-apps` 对所有进程返回 N/A），**单次 1.1~1.7 秒**，PS 冷启动占大头。
而 `CLEANUP_CACHE_TTL = 3.0`，界面每开一次性能页就付一次全价。

实测分解：

| 环节 | 耗时 |
|---|---:|
| `gpu_totals()`（nvidia-smi） | 63 ms |
| `_active_port()` | 0.1 ms |
| `_scan_procs_and_gpu(force=True)`（PowerShell） | **1119~1665 ms** |
| `cleanup_report()` 合计 | **1189 ms** |

**修法**：TTL 3s→20s，并新增后台线程 `_gpu_refresher()` 每 15s 预热
（间隔 < TTL，否则会漏窗）。

实测：**2.024 s → 0.067 s（30×）**。

### 4.3 还能继续做的（按性价比排序）

| # | 事项 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **降低 `parse_gguf` 的 Python 级分配量**：为跳过 tokenizer 的 `tokens`/`merges` 变长字符串数组，现在要**逐元素走**（单模型约 15 万个字符串对象、38 文件约 570 万次循环）。可改成「拿齐 `<arch>.*` / `general.*` 需要的键就停止解析」或按需跳过 `tokenizer.*` | 冷扫描 3851 ms → 目标 <100 ms；顺带压低常驻内存 | 中（要确认所需键都在 tokenizer 之前，得逐模型验证） |
| 2 | **启动时 `_do_scan()` 被跑了两遍**：`__main__` 跑一次，`_refresher` 的循环体在第一次 `sleep` 前又跑一次 | 修复前 = 2×1.2 GB；修复后因为缓存已几乎免费（但仍值一行注释/守卫） | 低 |
| 3 | **性能页轮询降频/改推送**：现在 `loadSys() + loadSlots()` 每 **2 秒**一次，`loadMgr()` 每 **5 秒**一次；`/api/system-metrics` 每次真算 nvidia-smi（62 ms，缓存 TTL 只有 1s） | 少一半 `nvidia-smi` 子进程；页面更省电 | 低 |
| 4 | **登录页改首页**：外壳 `open_path` 现在是 `/#/performance`，而这是**前端最大的单文件**（2781 行）且 `onMount` 里并发跑 5 个接口 | 冷启动首屏更快；日常主要用对话，落错页 | 低（改 `app/config.json` 的 `open_path`） |
| 5 | **0.7 GB 常驻的 Python 后端**：实测无人访问时 manager 工作集 738 MB 且稳定（不增长、无泄漏）。探针已排除：import 本身、`_do_scan()`、两个预热线程、`ThreadingHTTPServer` 与请求（这些都只占 411~413 MB） | 若能定位并降到 ~200 MB，对 32 GB 机器是白赚 | 低~中（尚未定位，需 tracemalloc 单独跑） |
| 6 | **首屏 2.49 MB JS**：两个 vendor chunk 占 2.34 MB。本地 HTTP 传输可忽略，主要是解析/执行成本 | 边际 | 低 |

> 关于 ⑤ 的探针数据（都已清理，结论留档）：
> 裸 import + 扫描 + 2 预热线程 = **410 MB**；再加 `ThreadingHTTPServer` + 打 20 次请求 = **413 MB**；
> 真实 manager 无人访问 = **738 MB**。差出来的 ~325 MB 仍在真实 `__main__` 路径上，未定位。

## 5. 功能与体验

### 5.1 现状盘点

**已有页面**：对话（`/`、`/chat/[id]`）、性能与模型（`/performance`）、参数（`/parameters`）、搜索（`/search`）。
**性能页 6 个区块**：实时资源 / 显存清理 / 服务器信息 / 模型切换 / 启动方案 / 磁盘上的模型。
**已有能力**：MCP（服务、资源浏览、预览）、工具、agentic、会话管理、备份、附件与多模态、上下文计量器、
模型下拉（右键菜单：启动配置与信息 / 按当前方案重启）、空闲 TTL、启动方案（9 字段）、显存预演。

**工具链**（`tools/`）：模型扫描校验、mmproj 配对测试、Ollama 硬链接同步、fit 探针、分层探针、
速度基准（`bench_speed.mjs` / `ab_bench.mjs` / `paired_bench.mjs`）、128K 基准、needle 检索测试、
`gpu_health.mjs`（功耗/温度/降频一条命令）、`ctx_speed_probe.mjs`、i18n 审计、字典去重与质检。

### 5.2 建议（按「用得上 × 成本低」排序）

#### A. 模型获取与选型 —— 目前最大的体验缺口

1. **应用内下载模型（HF / ModelScope）**。现在只能手动下好放 `models/hf/`，界面上只有「磁盘上有什么」。
   已有 `tools/model/hf_head_probe.mjs` 之类的探测脚本可以复用。带**进度、断点续传、SHA 校验**。
2. **在模型列表里直接标「这台机器能不能跑」**。`kv_shape`（n_layer/n_head_kv/k_len/v_len）**已经在
   `/api/models` 的返回里了**，`/api/fit` 也能预演 —— 把它提到列表行内显示「预计 X GB / 能否全层上卡」，
   用户就不用逐个点了试。
3. **给模型打标签 / 备注 / 收藏**。16 个模型里挑一个，目前只能靠名字认。

#### B. 加载与显存的可见性

4. **加载进度条**。首次发消息要加载 2~3 秒（大模型更久），目前只显示「生成中」。
   把 `-fit` 预演结果 + 实际加载进度串起来，用户才知道在等什么。
5. **空闲卸载要通知**。看门狗 300 秒卸模型是静默的，用户回来发现「模型没了」会困惑。
   托盘气泡或界面角标提示一次「已为省显存卸载 X，下次发消息自动拉起」。
6. **每模型「常驻」开关**。现在只有全局 `instance.autostart`；常用的那个模型应该能单独标记「不自动卸载」。
7. **把 `gpu_health.mjs` 的判断搬进界面**。那条「功耗上限 115 W 但只跑 40 W ⇒ 是整机预算」的判读口诀，
   做成性能页的一行提示，用户自己能判断「慢」是配置问题还是机器在限功耗。

#### C. 性能与基准

8. **一键跑基准并留档**。`tools/bench/bench_speed.mjs` 已经能测 tok/s，但结果散在终端里。
   在性能页加「测这个模型的速度」→ 结果存进 localStorage / 写回模型的备注，形成本机的模型排行榜。
9. **显存预算条**。现在只有 `vram_used/total` 两个数。画一条「当前模型 + 计算缓冲 + 桌面占用」的堆叠条，
   比数字直观得多（这个项目的显存知识已经非常完整，只差可视化）。

#### D. 工程卫生

10. **这个仓库没有版本控制**（README 明说）。`rollback\webui-built-*` 只留 3 份，是最脆的一环。
    建议上 git + `.gitignore`（README 里已列好该忽略什么），哪怕只在本地。
11. **`manager.py` 已 2120 行单文件**。可以按 `scan / fit / instances / metrics / http` 拆成包，
    单测也好写（现在只有 3 个测试脚本，没有 runner）。
12. **补齐启动脚本**：根目录三个 `start-*.bat` 与外壳功能重叠且参数口径不同（`-ngl 99` 硬编码，
    正是 MEMORY 里记过的 OOM 来源），建议统一或明确标注「仅调试用」。

## 6. 一句话总结

架构本身是**干净的**：三层职责清晰、两条通路不串、懒加载与空闲卸载共用一个入口、
中文走 overlay 不侵入构建产物。这一轮真正的收获是**后端有两个「一直在偷偷干活」的地方** ——
`_do_scan()` 每 30 秒白读 1.2 GB 磁盘烧 1 个核（已修）、`_sys_refresher` 从没启动导致 CPU 信息恒为 null（已修），
外加一次 1.2 秒的 PowerShell 开销被挪到后台（已修）。**体验上最该补的是「模型从哪来」** ——
现在只能手动放文件，这是整条链上唯一还需要用户动手的环节。
